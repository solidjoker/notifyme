# ARCHITECTURE.md — 三个循环怎么分工

## 一句话

**按入口拆，不按工种拆。** 一个循环管一个入口，从看到反馈一路做到发版、回复，中间不交接。循环之间不传话，没有总调度，共享的只有这个代码仓库。

## 全景

```
   GitHub issue / PR / Discord            X 关键词流
            │                                 │
            │                            便宜模型筛（去噪）
            │                                 │
            ▼                                 ▼
   ┌─────────────────┐              ┌─────────────────┐
   │    loop1        │              │    loop2        │
   │ 分诊→修→验→发版  │              │ 分诊→修→验→发版  │
   │ →回复           │              │ →回推           │
   └────────┬────────┘              └────────┬────────┘
            │                                 │
            └──────────┬──────────────────────┘
                       ▼
                 代码仓库（唯一共享物）
              AGENTS.md / LESSONS.md / 提交记录
                       │
                       ▼
              ┌─────────────────┐
              │    loop3        │
              │ 回头看前两个    │
              │ 清屎山/查恶意   │
              │ →写 LESSONS     │
              │ →拉黑           │
              └─────────────────┘

       人守的门：CI 配置 / 发布脚本 / 网络地址 / 凭据 / 依赖 / 审美
```

## 为什么这么拆

**求快的和求稳的分开。** loop1、loop2 的 KPI 是“一条反馈多快变成版本”；loop3 的 KPI 是“前两个有没有留下烂账”。放一个循环里，两个目标会互相打架——赶着发版的那个，不会主动把自己刚写的东西推翻。

**没有总调度。** 一旦有 Router 派单，Router 就成了单点和瓶颈。这里三个循环各自读仓库、各自决定下一件事，冲突靠 git 解决（本来也是唯一的真相源）。

**靠仓库协调，不靠消息。** 循环 A 不需要告诉 B 它改了什么——B 每轮开工先读 `LESSONS.md` 和 `git log`，自己就能知道。公告栏比邮箱可靠。

## 三个循环的职责边界

| | loop1 | loop2 | loop3 |
| --- | --- | --- | --- |
| 入口 | GitHub + Discord | X | 无外部入口 |
| 谁能触发 | 任何人 | 关键词命中的推文 | 定时（夜间） |
| 可以做 | 分诊、修、验、发版、回复 | 同左，回复推文 | 审查、写教训、拉黑、提整改 |
| **不许做** | 改自己的规矩文件 | 改自己的规矩文件 | 接外部需求、直接改业务代码 |
| 冲突时 | 先到先得（git） | 同左 | 只写建议，不改实现 |

loop3 明确**不接活**：它的提示词第一句就是“现在代码改动和 PR 合并完全是自动化的”，它只负责回头挑毛病。接了活它就会开始护自己的实现。

## 一轮循环长什么样

每个循环都是一样的骨架，只是入口不同：

```
1. 拉取（pull）           —— 本循环没处理过的反馈
2. 预筛（可选）           —— 便宜模型先扔掉明显不相关的
3. 分诊（triage）         —— 贵模型判断：值得做 / 不值得做 / 需要更多信息
4. 做（act）              —— 值得做的：调 coding agent 改代码
5. 验（verify）           —— 三类门：red/green、验收格式、危害清单
6. 交付（ship）           —— 提交（带验收记录）→ 发版 → 回复来源
7. 记账（journal）        —— 写日志，留给 loop3 回头审
```

第 3 步和第 7 步之间**不能有人工交接**——交接一次就多一次“等下一个接手”的延迟，而那正是这套东西要干掉的东西。

## 状态都在哪

| 东西 | 位置 | 谁写 |
| --- | --- | --- |
| 处理过的反馈 ID | `.loopstate/state.json` | 三个循环 |
| 每轮的详细日志 | `.loopstate/logs/<loop>-<date>.jsonl` | 三个循环 |
| 验收记录（结构化） | `.loopstate/acceptance/<id>.json` | coding agent 写，循环校验 |
| loop3 的审查报告 | `.loopstate/review/<date>.md` | loop3 |
| 规矩 | `AGENTS.md`、`LESSONS.md`、`docs/*` | 人 + loop3 |
| 拉黑名单 | `config/blocklist.txt` | loop3 追加，人删除 |

`.loopstate/` 不入库（见 `.gitignore`），它是一次性的工作记忆；**要留下来的东西必须进仓库**，否则下一轮就没人读得到。

## 人守在哪

不是守流水线，是守门口：

- **审美**：UI/UX 好不好看，人说了算。
- **会出大事的门**：CI 配置、发布脚本、网络地址、凭据、依赖。清单见 `docs/COMMUNITY_RULES.md`。
- **做什么不做什么**：循环谁提需求就接谁，功能会无限膨胀。做哪个不做哪个，得有人拍板。

## 两个必须自己补的窟窿

抄这套设计之前想清楚：

1. **功能膨胀。** 流水线没有“不做了”的机制。要么把功能切成可关的插件，要么定期砍。
2. **提示注入。** 推文和 issue 正文是外部可控文本，而循环又能自己发版。原文没写这条怎么防，必须自己加：
   - 读消息的权限和发版的权限，**分给不同的循环**；
   - 外部文本进 prompt 时，明确标成不可信数据块，不拼进指令区；
   - 发版前要求人工签一次（或者至少要求 CI 双人）。
