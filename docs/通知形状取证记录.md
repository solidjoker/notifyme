# 通知形状取证记录（微信 / 飞书 / 钉钉 / 未知 App）

> 状态：**已取证（微信、钉钉）+ 口径已固化**；飞书 仍缺真机样本（设备上当前无飞书通知）。
> 关联里程碑：M2「跨应用通知管理」；任务清单第 2 项、验收第 2 条。

## 1. 为什么要这份记录

M2 把通知来源从微信专用改成通用「应用源」注册表（`AppSourceRegistry`）之后，
飞书 / 钉钉走 `PrefixImParser`，未收录 App 走 `GenericNotificationParser`。
解析器的边界用例（分隔符形态、前缀长度上限、空正文丢弃等）早就有了单测，
但**「某家 App 真实通知长什么样」这个前提本身**一直没有落纸的证据。

2026-11-12 在真机（Xiaomi 25098PN5AC / Android 17）上完成了微信与钉钉的取证，
并且**取到了与假设相反的事实**：微信通知绝大多数不带 `MessagingStyle`，正文是
`[11条]发言人: 正文` 这种纯文本形态。按旧代码，这类消息全部被判成私聊、
发送者被写成会话名，且未读数一变就产生一条重复消息。
这份记录把取证结论、修正后的口径、以及还缺的东西固定下来。

## 2. 取证方法

### 2.1 看真实通知形状

```powershell
# 列出该包当前所有活跃通知（含 extras 展开）
adb -s <serial> shell dumpsys notification --noredact <pkg>

# 全量（含已消失的通知历史），再按包名切片
adb -s <serial> shell dumpsys notification --noredact > notif-dump.txt
```

关键字段（只列解析器实际读的）：

| 字段 | 含义 | 解析器怎么用 |
|---|---|---|
| `android.title` | `EXTRA_TITLE`，通常是会话名 | 会话名 `conversation`；为空回落 appLabel → pkg |
| `android.text` | `EXTRA_TEXT`，折叠态正文（系统可能截断） | 无 bigText 时作为正文 |
| `android.bigText` | `EXTRA_BIG_TEXT`，展开态全文 | 有值时**优先**作为正文 |
| `android.subText` | `EXTRA_SUB_TEXT`，副标题 | 仅在前两者都空时兜底 |
| `android.messages` | `EXTRA_MESSAGES`，MessagingStyle 逐条明细 | 有值时**优先**（最可靠） |
| `pkg` / `postTime` | 包名 / 发布时间 | 直接入库字段 |

其余字段（`tickerText`、`category`、`flags`、`smallIcon`、`color` 等）由
`NotifyMeListener` 过滤或忽略，与入库口径无关。

### 2.2 看聊天页控件 id（a11y 直读用）

```powershell
adb -s <serial> shell uiautomator dump
adb -s <serial> shell cat /sdcard/window_dump.xml   # 搜 resource-id
```

## 3. 真机取证结果（2026-11-12）

### 3.1 微信（`com.tencent.mm`）

```text
tag=null  channel=message_channel_new_id
extras:
  android.title   = String (<会话名>)
  android.text    = String ([11条]<发言人>: 好的，谢谢)
  android.showWhen= Boolean (true)
```

结论四条：

1. **没有 `MessagingStyle`**：全量 dump 里 `android.messages` 出现 **0 次**、`android.conversationTitle` **0 次**；
   `android.bigText` 全文只出现 6 次且都不属于微信。旧 `WeChatNotificationParser` 的 style 分支在真机上几乎不命中。
2. **正文自带未读计数前缀**：`[11条]`、`[16条]` —— 数字随未读数递增。
3. **发言人用半角冒号且冒号后无空格**：`[11条]<发言人>: 好的，谢谢`。
4. **`subText` 为 null**，没有额外的会话名信息。

入库数据侧的量化（`files/messages.jsonl` 1798 行，微信 1595 条）：

| 观察 | 数值 |
|---|---|
| 微信 `isGroup` | **全为 0**（1595 条无一判成群聊，包括 676 条带 `[N条]发言人:` 的） |
| 带 `[N条]发言人: 正文` 的会话 | 93 个会话中 61 个出现，其中 28 个会话出现 **≥2 个不同发言人**（真群聊） |
| 剥掉未读前缀后的重复组 | **78 组，多出 271 行**（文本完全相同含前缀的 60 组 / 218 行） |
| 重复对的相邻时间差 | >10min 221、≤10min 19、≤30s 14、≤2min 9、≤5s 8 |

第 3 行是这轮最硬的证据：**未读数从 `[11条]` 涨到 `[12条]`，去重键（含正文原文）就变了**，
同一句话被当成新消息再存一次。这是数据层的重复，不只是显示问题。

### 3.2 钉钉（`com.alibaba.android.rimet`）

```text
tag=null  channel=mipush|com.alibaba.android.rimet|101344  opPkg=com.xiaomi.xmsf
extras:
  android.title = String (钉钉｜<群名>)
  android.text  = String (<发言人>(老师):「11月12日班级通知」通知确认情况)
  message_id / xmsf_target_package / eventMessageType = String(1000)
```

结论三条：

1. **标题形如「钉钉｜<群名>」**（全角竖线 `｜` 作前缀分隔），会话名取标题即可，但展示层会带「钉钉｜」这三字。
2. **正文是「发言人(角色):正文」**，半角冒号、**冒号后无空格**。
3. **经小米推送代发**（`opPkg=com.xiaomi.xmsf`），所以 extras 里混有 `xmsf_target_package`；解析器只读 title/text，不受影响。

### 4.1 抽取口径（`NotificationTextCore`）

| 步骤 | 规则 | 理由 |
|---|---|---|
| ① 剥未读前缀 | `^\[\s*\d+\s*条\s*\]\s*`；剥完为空则**保留原文** | 前缀随未读数变化，留在正文里会破坏去重 |
| ② 切发言人 | 依次试 `：` / `: ` / `:`；前缀长度 1–20、非空、不含换行、正文非空 | 真机三种形态都有 |
| ③ 驳回可疑前缀 | 前缀含**任意空白**直接否；半角冒号再加：长度 ≥2、非纯数字、正文不以 `//` 开头 | 「明天 10:30 开会」不能被切成 sender=明天 |
| ④ 判群聊 | 前缀 == 会话名 → 私聊；会话名**包含**前缀（真机形如 `张三_某机构_某班`）→ 私聊；否则群聊 | 会话名会拼接来源后缀，等值比较不够 |
| ⑤ 无前缀 | 整串当正文，sender=会话名，isGroup=false | 群聊里也会有纯文本行（实测 28 个群会话全部含纯文本行） |

### 4.2 已知的口径副作用（写清楚，不藏）

- **第 6 条的冒号被吞**：前缀与会话名相同时只切掉前缀，`isGroup` 保持 false。
  归属信息不丢（标题已是对方名），丢的是「冒号」这个输入噪声。
- **正文以「提醒：」开头会被当成发言人**（如「提醒：明天放假」→ sender=提醒）。
  这是归属展示层面的偏差，不影响入库与去重；`NotificationParserTest` 里有用例记录现状。
- **前缀超过 20 字不切**：宁可整句保留也不猜。
- **未收录 App 只剥未读前缀、不猜发言人**：`GenericNotificationParser` 没有该 App 的会话名语义，
  猜错会把正文切半，成本高于收益。
- **已经入库的历史数据不会被自动修正**：口径修正只影响新消息。需要清理历史重复行时，
  在设备上执行「设置 → 数据 → 规范化」（`MessageStore.normalizeSchema`）——只补字段，不删重复。
  去重键里含正文原文，历史重复要人工核对后再删（会话详情页支持多选删除）。
