# 通知形状取证记录（飞书 / 钉钉 / 未知 App）

> 状态：**口径已固化，真实 dump 待真机补**。
> 关联里程碑：M2「跨应用通知管理」；任务清单第 2 项、验收第 2 条。

## 1. 为什么要这份记录

M2 把通知来源从微信专用改成通用「应用源」注册表（`AppSourceRegistry`）之后，
飞书 / 钉钉走 `PrefixImParser`，未收录 App 走 `GenericNotificationParser`。
解析器的边界用例（分隔符形态、前缀长度上限、空正文丢弃等）早就有了单测，
但**「某家 App 真实通知长什么样」这个前提本身**一直没有落纸的证据。

后果：解析器「刻意保守」——宁可把整句当正文，也不猜发言人。
保守是对的，但保守到什么程度、会不会把常见形态也判错，只能靠真实通知验证。

这份记录把**当前代码实际遵循的解析口径**固定下来（`NotificationShapeEvidenceTest`），
并把「还缺什么」写清楚，避免下一轮又从头猜。

## 2. 取证方法

### 2.1 看真实通知形状

```powershell
# 列出该包当前所有活跃通知（含 extras 展开）
adb -s <serial> shell dumpsys notification --noredact <pkg>
```

关键字段（只列解析器实际读的）：

| 字段 | 含义 | 解析器怎么用 |
|---|---|---|
| `android.title` | `EXTRA_TITLE`，通常是会话名 | 会话名 `conversation`；为空回落 appLabel → pkg |
| `android.text` | `EXTRA_TEXT`，折叠态正文（系统可能截断） | 无 bigText 时作为正文 |
| `android.bigText` | `EXTRA_BIG_TEXT`，展开态全文 | 有值时**优先**作为正文 |
| `android.subText` | `EXTRA_SUB_TEXT`，副标题 | 仅在前两者都空时兜底 |
| `android.messages` | `EXTRA_MESSAGES`，MessagingStyle 逐条明细 | 有值时**优先**（最可靠） |
| `pkg` / `postTime` | 包名 / 发布时间 | 直接入库字段 |

其余字段（`tickerText`、`category`、`flags`、`smallIcon`、`color` 等）由
`NotifyMeListener` 过滤或忽略，与入库口径无关。

### 2.2 看聊天页控件 id（a11y 直读用）

```powershell
adb -s <serial> shell uiautomator dump
adb -s <serial> shell cat /sdcard/window_dump.xml   # 搜 resource-id
```

## 3. 当前解析口径（已固化，有测试）

`app/src/test/java/com/notifyme/android/NotificationShapeEvidenceTest.kt`（10 条）——
把「真实通知形状 → 入库字段」的映射写死，改解析器或改监听器抽取字段时它会先红。

| # | 场景 | 输入形态 | 期望入库 |
|---|---|---|---|
| 1 | 飞书 单人群通知 | title=王五，text=明天下午三点的评审改到周五了 | sender=王五 / text 同输入 / isGroup=false |
| 2 | 飞书 群通知（全角冒号） | title=项目攻坚群，text=李四：接口文档我更新好了 | sender=李四 / text=接口文档我更新好了 / isGroup=true |
| 3 | 飞书 群通知（展开态） | text=赵六：周末加班，bigText=赵六：周末加班需要两位同学支持 | 取 bigText 切出 sender=赵六 |
| 4 | 钉钉 群通知（半角冒号+空格） | title=运维值班群，text=张三: 生产库告警已经恢复了 | sender=张三 / isGroup=true |
| 5 | 钉钉 群通知（有 MessagingStyle） | text=（3 条）…，messages=[李四, 王五] | 取最后一条 sender=王五 / text=收到 / timestamp=消息自带 |
| 6 | 钉钉 私聊（前缀=会话名） | title=项目经理，text=项目经理: 明天上午十点对齐进度 | sender=项目经理 / text=明天上午十点对齐进度 / **isGroup=false**（冒号被吞） |
| 7 | 未收录 App 回落 | title=短信通知，text=您的快递已到驿站 | sender=会话名 / isGroup=false |
| 8 | 路由不混 | — | 飞书/钉钉 → `PrefixImParser`；其余 → `GenericNotificationParser` |
| 9 | 时间戳缺失 | style 的 timestamp=0 | 回落 `postTime` |
| 10 | 空正文 | text 全空白 | 不入库（返回 null） |

### 3.1 已知的口径副作用（写清楚，不藏）

- **第 6 条的冒号被吞**：`PrefixImParser.splitSenderPrefix` 不看会话名，切出 `(项目经理, 明天上午十点对齐进度)`；
  `isGroup` 由 `sender != null` 决定，而 `sender` 又被 `= conversation` 过滤掉，最终 isGroup=false。
  归属信息不丢（标题已是对方名），丢的是「冒号」这个输入噪声。
- **正文以「提醒：」开头会被当成发言人**（如「提醒：明天放假」→ sender=提醒）。
  这是归属展示层面的偏差，不影响入库与去重；`NotificationParserTest` 里有用例记录现状。
- **前缀超过 20 字不切**（`MAX_SENDER_PREFIX_LEN`）：宁可整句保留也不猜。
